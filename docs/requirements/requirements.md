## 1. 背景と目的
- ブランド／テンプレを持つチームが短時間で提案書を量産できるフローを提供し、パワーポイント資料を扱う全メンバーの作成負荷を大幅に軽減する（導入先は社内外を問わない）。
- 生成物のビジュアル品質をブランドガイドラインに沿って均一化し、人的手直しを最小限に抑える。
- Mac／Linux／Windows の各環境において同一フローで運用できる自動生成基盤を提供する。

## 2. スコープ
- テンプレートからレイアウト構造・ブランド設定を抽出し、再利用可能なレイアウト仕様として管理する。
- Markdown/JSON/TXT/PDF/URL など複数フォーマットの資料を正規化し、章構成付きのコンテンツドラフトを作成する。
- HITL と自動処理を組み合わせてコンテンツドラフトをレイアウト仕様へ割り当て、テンプレ準拠の構成データを生成する。
- dynamic モード: レイアウト候補から自動選択し、構成を柔軟に入れ替えられる。
- static モード: あらかじめ決めたレイアウト枠に内容を固定割り当てし、用意された枠を漏れなく埋めることを重視する。
- 抽出済みテンプレと構成データから PPTX を描画し、任意で PDF 変換、仕上げツールと品質診断を実行して監査ログ付きで出力する。
- 監査ログ・通知・フック・設定管理を通じ、環境差異やブランド差異を吸収しつつクロスプラットフォームで運用する。

## 3. 利用者とユースケース
- 主利用者: このツールを導入する組織のパワーポイント利用者全般。
- 想定ユースケース
  - 資料データ（Markdown/JSON/PDF/URLなど）を渡し、1分以内にテンプレ準拠のドラフト PPTX を生成してレビューを開始する。
  - 急な会議・提案依頼で、テンプレと既存アウトラインを使って待ち時間なく生成し、必要に応じて PDF も同時出力する。
  - 既存 PPTX を読み込み、レイアウト逸脱や余白・スタイルの問題を検出し、仕上げと合わせて自動補正を適用する。
  - 章立てやスライド構成が決まっている案件で、決めたレイアウト枠にコンテンツを固定割り当てし、枠漏れを防いだうえで出力する。

## 4. 機能要件 - 共通機能
### 4.1 入力仕様管理
- テンプレート資産（Stage1 入口）
  - 要件: テンプレート PPTX とブランド定義を受け取り、後続ステージが参照できるレイアウト仕様を抽出・保持できること。
  - 条件: テンプレ版やアンカー命名などテンプレ依存情報を再利用可能な形で管理し、以降のステージで参照できること。
- コンテンツ資産（Stage2 入口）
  - 要件: Markdown/JSON/TXT/PDF/URL など多様な資料を受け取り、スライド単位のカード（タイトル/見出し、本文ブロック、注記、配置希望）へ正規化できること。
  - 条件: 案件単位でスタイル上書き（フォント・色・余白・階層）を許容し、必須フィールド欠落や型不整合は検出できること。
- 外部フック・設定（任意）
  - 要件: ステージごとの処理を拡張するフックや設定ファイルを任意で受け入れられること。
  - 条件: フックの依存はテンプレート資産と並置して管理し、指定されたときのみ実行する。

### 4.2 PPTX 自動生成
- レンダリング範囲: テンプレートを基に無人で PPTX を生成し、タイトル/本文/箇条書き/表/チャート/画像を扱えること。
- スタイル適用: 段落・フォント・配色・余白・行間・揃え・インデントなどレイアウト固有のスタイルをテンプレから自動抽出し、レンダリング時に忠実に適用できること。アンカー指定時はテンプレ図形名を保持すること。
- 品質維持: レンダリング段階で段落スタイルを完結させ、仕上げ処理はフォールバック対応と監査ログ出力にとどめること（段落補正は原則レンダリング内で完結）。
- 実行形態: オフィスアプリを起動しないヘッドレス実行で完結できること。

### 4.3 品質診断
- 検出対象: レイアウト・スタイル逸脱（余白/グリッド/揃え/フォントサイズ/コントラスト）、階層構造の異常（箇条書き深さや段階ジャンプ）、空要素など可読性・配置上の問題を検出できること。
- 記録: スライド/オブジェクト単位のメトリクスと検出結果を診断ファイルに出力し、重大度と推奨修正を付与できること。
- 連携: 後続の仕上げ処理や監査ログで再利用できる形式（ID/座標/スタイル情報など）で保持すること。

### 4.4 自動補正
- 適用条件: オプションを有効にした場合のみ自動補正を行い、無効時は補正しない。
- 自動補正（プログラムによる仕上げ）: 安全なレイアウト/スタイル調整に限定し、位置合わせ、空要素処理、最小フォント/コントラストの引き上げ、段落階層の制約などを自動で適用できること。適用内容はログ/診断に記録し、後続レビューで確認できること。
- 自動補正（生成 AI による改善案）: 文言の言い換えや要約、箇条書きの整形、軽微なレイアウト修正などの提案を自動生成し、必要に応じて適用できること。提案と適用有無はログに残し、後から再生・監査できること。
- 制御: 補正の有効/無効とルール単位のオン/オフを設定で切り替えられること。

### 4.5 出力と配布
- 成果物: PPTX を生成し、オプションで PDF も生成できること。出力パスとバージョン/ハッシュなどのメタ情報を保持すること。
- 通知: 保存先 URL と生成メタ情報（生成時刻、テンプレ版、ジョブ ID 等）を通知できること（チャネルは任意）。
- 一貫性: PPTX/PDF は監査ログと突合できるようハッシュや出力先を記録すること。

### 4.6 監査・ログ
- 記録対象: 入力/テンプレ/生成成果物のバージョン・ハッシュ、処理時間、実行オプション、警告/エラーを監査ログに記録できること。
- トレーサビリティ: スライドや成果物 ID と監査ログを紐づけ、後続ステージや承認ログと突合できること。
- 障害対応: 失敗時に原因、再実行手順、関連ファイルパスを残すこと。
- 一貫性: PDF や仕上げ処理の結果も同一監査ログから参照できること。

### 4.7 HITL 承認フロー
- 対象: コンテンツ構成とレイアウト割り当てを扱う stage 3（Compose）で、人による承認・差戻し・部分承認が可能であること。
- 記録: `slide_id`、操作種別（approve/return/partial）、実行者、時刻、理由コードをログに記録し、後続ステージや監査ログと突合できること。
- ロック: 承認済みスライドはロックされ、差分生成・再レビュー時に保持されること。
- 可視性: 承認ステータスを成果物メタ（例: generate_ready_meta）に反映し、監査ログからも参照できること。

## 5. 機能要件 - 個別機能
### 5.1 Stage 1: テンプレ構造抽出
- テンプレート PPTX からレイアウトとプレースホルダの構造を抽出し、後続ステージが参照できる仕様として提供できること（レイアウト識別子、プレースホルダ情報、用途タグ、メディアヒント等）。
- アンカー命名や用途タグをテンプレ定義に沿って正規化し、不整合を検出・報告できること。
- 抽出結果を検証し、重大なエラーが解消された状態をリリース判定条件とできること。

### 5.2 Stage 2: コンテンツ準備
- 多様な入力形式（Markdown/JSON/TXT/PDF/URL など）を受け取り、スライド単位のカードに正規化し、章構成やメタ情報（生成モード、インポート元、ログ）を保持できること。
- ダイナミック/固定レイアウトのモードを必須指定とし、欠落や整合不一致は検出・報告できること。
- 案件単位のスタイル上書きや必須フィールドの検証を行い、不正入力はエラーにできること。

### 5.3 Stage 3: マッピング・構成設計
- カードとレイアウトを突合し、候補スコア評価やフォールバック（分割や付録送りなど）を経て構成データを生成できること。
- ダイナミック/固定割り当てのモード整合を保ち、割り当て不能や必須枠未充足はエラーとして扱えること。
- 承認・差戻しログやマッピングログを残し、フォールバックや AI 補完の痕跡を監査できること。

### 5.4 Stage 4: レンダリング・エクスポート
- 構成データとテンプレを用いて PPTX を描画し、テンプレスタイルを適用した上で出力できること。
- オプションで PDF 変換や仕上げ・診断を実行し、その結果を監査ログと突合できること。
- 出力物のハッシュやメタ情報を保持し、後続の配布・監査で参照できること。

### 5.5 ステージ間ハンドオーバ
- Stage2 で生成したカード・ログ・モード情報を Stage3 で受け取り、モード整合（ダイナミック/固定）と必要ファイルの有無を検証できること。
- Stage3 の構成データを Stage4 へ渡し、テンプレ側のスタイルやメタ情報と突合できること。
- 各ステージ間の主要成果物（カード/構成データ/PPTX・PDF/監査ログ）が参照可能であること。

### 5.6 テンプレ運用サポート
- テンプレ版ごとの差分検出と互換レポートを生成できること。リリースメタ（作成者/ブランド/バージョン/レビュー日）を保存できること。
- ゴールデンサンプルや診断結果を集計し、品質メトリクスとして追跡できること。
- 外部フックやマッピング設定をテンプレ単位で委譲でき、必要な依存を併置して管理できること。

## 6. 非機能要件
- パフォーマンス: 30 スライド程度の提案書を 1 分以内に生成できることを目標とする。テンプレ構造抽出は 1 ファイル 30 秒以内を目標とする。
- 可用性: 失敗時に再実行できる冪等性とジョブ管理を備えること。
- 拡張性: 追加レイアウトや新たな評価ルールを設定ファイルの変更で反映できること。
- 可観測性: 各ステップの処理時間、失敗率をモニタリングできること。
- 国際化: 日本語フォントを既定としつつ、英語への拡張が可能な構造とすること。
- クロスプラットフォーム: Mac／Linux／Windows で同一コマンドが実行できること。
- HITL 運用: 承認 UI のレスポンスは 3 秒以内、承認 1 件あたりの平均処理時間は 5 分以内を目標とする。
- AI レビュー: 自動レビューは 10 スライドあたり 30 秒以内に完了し、Auto-fix 提案の適用率を計測できること。

## 7. 運用要件
- テンプレート・ブランド設定の版管理と適用履歴の把握。
- `template_release.json`（テンプレ受け渡しメタ）と差分レポートの保管。
- CI/CD 環境で自動テストおよび自動デプロイを実行可能にすること。
- CI では SonarCloud 静的解析を毎回実行し、README へライセンス・CI・Python バージョン、および SonarCloud（Quality Gate / Coverage / Bugs / Vulnerabilities / Code Smells / Maintainability / Reliability / Security / Duplicated Lines）のバッジを掲載して最新状態を示すこと。
- 定期的なジョブ結果通知とアラート通知を行い、一次対応手順を明文化すること。
- 生成物のストレージ保存期間（初期値 90 日）と削除ポリシーを設定すること。
- 承認ログと生成ログを相互参照し、監査時にスライド単位の変更履歴を追跡できること。

## 8. セキュリティ・コンプライアンス要件
- 入力データに含まれる機密情報を暗号化保存し、アクセス権限を RBAC で制御すること。
- LLM など外部 API を利用する際は匿名化・マスキングを行い、送信ログを保持すること。
- ライブラリの脆弱性監視を定期実施し、重大な脆弱性は迅速に是正すること。
- アクセスログに利用者 ID、操作内容、タイムスタンプを記録し、監査に対応できること。
- 社外展開時はブランドライセンスとデータ取り扱い条件を導入組織側で定義し、RBAC・監査ログの境界設定を適用すること。

## 9. 制約・前提
- オフィスアプリケーションを起動しないヘッドレス実行が前提。
- Python を主要言語とし、補助ツールに .NET を用いる場合はクロスプラットフォーム対応ライブラリに限定する。
- ネットワーク制限下でも基本機能が動作するよう、外部通信は設定で切り替え可能とする。
- 画像は連携済みロゴのみ使用し、外部画像取得・生成は行わない。チャート／グラフはテキストで構造化可能なデータのみ表形式で表現する。
- テンプレ改訂時は `.pptx` のみを対象とし、`extract-template` による構造抽出と互換性検証を必須とする。

## 10. 将来拡張要求 (参考)
- Office.js アドインによるワンクリック整形機能の追加。
- LLM を活用したレビューコメント生成や自動校正機能の拡張。
- 既存 PPTX から JSON 仕様を逆生成するリバースエンジニアリング機能。
- 多言語対応、画像生成連携、Keynote/Google Slides 互換出力。
- 承認ログ・生成ログ・監査ログを統合したリアルタイム監査ダッシュボード。

## 11. 未決定事項
- 正式なブランドカラー、フォント、禁則ルールの確定。
- 監査ログ保存基盤の選定と保持期間。
- 監査ログファイルの外部保存・モニタリング連携（CLI では `audit_log.json` を出力済み、基盤連携は未決）。
- LLM／視覚モデルのホスティング方式（オンプレミス／クラウド）。
- ジョブ実行プラットフォーム（Azure Functions, Container Apps, AWS Lambda, GCP Cloud Run 等）の最終決定。
- 社員向け配布ポータルの提供方法。
- テンプレ差分通知の実装方式と配信チャネル。
- HITL 承認 UI を提供するプラットフォーム（バックログ、現状は API / CLI 運用）の選定。
- Open XML Polisher と PDF 変換ジョブの配置（CLI 内包 / 外部サービス）。
