## 背景
- RM-068 実施により `ContentElements.body` の 6 行 / 40 文字制約を撤廃し、上流 stage でのテキスト削減を行わない方針へ転換した。
- 今後はレイアウト許容量を超えるオーバーフローをどの stage で、どの手段で解決するかを設計する必要がある。
- テンプレート（Stage3/4）が許容上限を定義し、Stage2 は LLM による自由生成を維持する思想をベースに議論を実施した。

## 議論まとめ
1. **stage ごとの責務整理**
   - テンプレートは PowerPoint 側のレイアウト制約（文字数・行数など）の取得源とする。
   - Stage2（prepare）は LLM による自由生成を担い、文字数などのハード制約は課さない。
   - Stage3（compose）はテンプレ容量と生成内容を突き合わせ、最適なレイアウト選択や警告記録を行う。
   - Stage4（gen）は選定済みレイアウトのレンダリングに専念し、最終的な見た目を仕上げる。

2. **オーバーフロー対処候補**
   - **優先1:** LLM による要約で情報量を圧縮する。
   - **優先2:** 必要に応じて文字サイズを縮小し、レイアウト内に収める（ブランド下限を設定する）。
   - **非推奨:** オブジェクトのサイズを拡張して対応する（レイアウト崩れのリスクが高いため回避）。

3. **組み込みタイミング（案）**
   - Stage3（MappingStep）でオーバーフローを検知した際、まず警告ログを出力しつつ LLM 要約を自動提案（patch_ai として記録）する。
   - Stage4（SimpleRefinerStep）で残ったオーバーフローに対し、ブランド許容範囲内でフォントサイズ調整をフォールバックとして適用する。
   - いずれの処理も監査ログ・警告に記録し、HITL が差戻し判断を行える状態を維持する。

4. **今後のタスク化**
  - 上記方針を新規ロードマップ項目として管理し、要約アルゴリズム・フォント縮小ヒューリスティック・設定値の検討を進める。
  - 実装時は Stage3/Stage4 のフラグ設計、patch_ai ログ整備、ブランド設定との整合確認を要件に含める。
