## 背景
- `external/sample/stage04_gen.py` でテンプレートレイアウトから図形を `deepcopy` する際、スライド側の `.rels` にリレーションを追加しておらず PowerPoint が修復ダイアログを表示する事象を確認。
- `generate_ready.json` から生成した PPTX を `python-pptx` および `unzip` で検証した結果、`slide1.xml` に `rId7` 等の参照がある一方で `_rels/slide1.xml.rels` には登録が無いことを把握。
- 一時的に `deepcopy` ブロックを無効化して再生成すると修復ダイアログは消滅するが、テンプレートの装飾や表が消えるため恒久対応が必要。

## 検知方針
- 生成済み PPTX の各スライドについて `r:embed` / `r:id` を列挙し、対応する `_rels/slideN.xml.rels` に同一 ID の `Relationship` が存在するか確認するスクリプトを追加する案を合意。
- 欠落リレーションを検出できれば CLI 実行時に警告を出し、PowerPoint 修復リスクを早期に把握できる。

## 恒久対応方針（案2 採用）
- テンプレート側にプロトタイプスライド（実スライド）を事前に用意し、Stage4 は既存図形の内容だけを書き換える方式へ移行する。
- これに合わせて Stage1 (template 抽出) を拡張し、実スライドが存在する場合はそちらから `template_spec.json` / `jobspec.json` を構築、存在しないレイアウトのみ従来どおりスライドマスターから生成する仕様を新規 RM として実装する。

## 今後のタスク
1. 生成 PPTX のリレーション欠落を検知するユーティリティを `scripts/` 配下に追加する。
2. 実スライド優先で blueprint / spec を構築できるようテンプレート抽出ロジックを拡張する（新規 RM を起票し最優先で対応）。
3. Stage4 外部フックからレイアウトの `deepcopy` 処理を撤廃し、テンプレート内プロトタイプを複製するフローへ置き換える。

## 備考
- `templates/sample.pptx` のレイアウトにはプレースホルダー 3 個、非プレースホルダー図形 11 個が存在するため、現状のレイアウト複製をやめるにはプロトタイプスライド整備が必須。
- Excel マッパー (`temp/excel/excel_mapper.py`) は既存スライドを前提とした差し替え方式であり、今回の方針転換のリファレンスとして活用できる。
