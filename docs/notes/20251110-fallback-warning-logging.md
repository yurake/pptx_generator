# フォールバック発生時のエラー化方針整理

## 背景
- CLI やパイプラインでは、ユーザー指定が無効だった場合に既定値へフォールバックするケースが複数存在する。
- 旧方針では `fallback_report.json` など成果物へ記録しつつ処理を継続していたが、失敗を見落とすリスクが高かった。
- ユーザー要望により、フォールバックは許容せず即座にエラーとして扱う方針へ改める。

## 現行実装の観測
- `MappingStep._apply_capacity_controls`（`src/pptx_generator/pipeline/mapping.py:553`）はレイアウト収容超過を検知すると `MappingFallbackState` に記録し、`fallback_report.json` へ出力するが `logger.warning` は出さない。
- `mapping_log.json` にも `fallback.history` が保存されるが、CLI 標準出力にアラートは出ない。
- ブランド設定や anchor 解決など別のフォールバック箇所でも、既定値使用は静かに処理されるケースが多い。
- 一方で `draft_document artifact の型が不正のため簡易ドラフトを生成します` など、類似状況で `logger.warning` を出している箇所もあり統一されていない。

## 新方針
- フォールバック経路は廃止し、期待するリソースが得られない場合は `PipelineFallbackError` を送出する。
- 例外送出前に `logger.error` で詳細（スライド ID、アンカー名、ファイルパスなど）を出力し、CLI 標準出力とログファイルから即座に原因を把握できるようにする。
- `fallback_report.json` はフォールバック発生時のみ生成するが、例外化により原則出力されない想定である。
- テストでは例外発生とエラーログの出力を検証し、フォールバック復活を防止する。
- LLM クライアント（template_ai/layout_ai/content_ai/prepare）でも代替モデルやパラメータ調整による継続実行を禁止し、初回呼び出しが失敗した時点で例外を送出する。

## 次ステップ案
- RM-065 で Mapping / Renderer を優先的に例外化し、アンカー欠損・テンプレート不整合・ドラフト未生成などを検知したら即座に停止させる。
- ブランド設定やテンプレート抽出など他コンポーネントのフォールバックも調査し、同様に例外化する。
- 運用手順（`docs/runbooks/`）に、エラー発生時の確認項目とリカバリー方法（Spec/テンプレ/ブランドの再生成など）を追記する。
