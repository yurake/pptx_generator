# タスク管理方針

## 方針
- リクエストを正しく認識し、RMが特定されToDo骨子、ブランチの準備を、Plan作成の前に必ず行う。
- Approval-First を徹底し、Plan 承認前に実装やドキュメント更新を行わない。
- 作業ログと意思決定は ToDo（`docs/todo/`）へ集約し、必ず記録に残す。

## プロセス
以下の流れを順番どおりに進める。
1. リクエスト認識と RM 確認  
   ユーザーと依頼内容・対象 RM をすり合わせ、既存 ToDo の有無を確認する。
2. ToDo 骨子とブランチ準備  
   テンプレートから ToDo を作成し、`目的`・`roadmap_item`・`関連ブランチ` を入力したうえでブランチを `feat|fix|chore|docs/rmxxx-<slug>` 形式で作成する。
3. Plan 作成と承認取得  
   スコープ／影響範囲／リスクなどをまとめた Plan を提示し、承認後に ToDo の「計画策定」欄へ全文転記する。
4. 実作業着手  
   上記を満たしたのちに初めて実装・ドキュメント更新を行い、作業ログや判断は ToDo へ記録する。

### リクエスト認識と RM 確認
- リクエストの内容に不明点があればユーザーに聞き返し、認識合わせを行う。
- リクエスト内容を元に対象 RM が存在するか`docs/roadmap/roadmap.md`から確認し、ない場合は新規であることをユーザーに確認する。
- 原則はいずれかのRMに紐づく作業である。ただしユーザーから「対象となるRMなし」と明示された場合のみ、例外的に対象特定をスキップする。
- `git status` がクリーンであることを確認する。
- 既存の ToDo／ブランチが存在する場合は最新の状態かを確認し、必要があれば更新する。

### ToDo 骨子とブランチ準備
- ToDo は `docs/todo/` 配下で作業ログを一元管理し、フロントマターの `目的`・`関連ブランチ`・`関連Issue`・`roadmap_item` を必ず埋める。`roadmap_item` には対象の `RM-xxx テーマ名` を記載し、`RM-000` はロードマップ整備・横断タスク専用とする。
- ToDo ファイル名は `YYYYMMDD-rmxxx-<slug>.md` とし、`rmxxx` はロードマップ番号に一致させる。旧形式はアーカイブに残すが、新規作成時は必ず `RM-xxx` を含める。
- ToDo・Plan では目的・参照資料・完了条件を簡潔に記載し、詳細手順は `docs/policies/context-engineering.md` が示す下位ドキュメントへ誘導する。
- 原則必ず ToDo を新規作成する。ユーザーから「ToDo は作成不要」と明示された場合のみ、例外に的に作成をスキップする。
- ToDo を起票する時点で、作業ブランチの作成・初期コミット・最初の push を完了させる。チェックリストの「ブランチ作成」項目が未完の場合は、Plan 作成フェーズへ進まない。
- Todoの利用方法について必ず`docs/todo/README.md`を参照すること。

### Plan 作成
- **Plan 提示の必須化**: バグ修正・機能追加を問わず、実装前に scope／対象ファイル・モジュール／想定影響ファイル／リスクと前提／テスト戦略（単体・統合など）／ロールバック方法を箇条書きでまとめた Plan を提示し、ユーザーの承認を得るまで作業を開始しない。承認後は Plan の記載内容を該当 ToDo の「計画策定」チェック項目のメモ欄へそのまま転記し、Plan と ToDo の内容を常に一致させる。
- **承認の記録**: 承認を得たメッセージのリンクまたは ID を ToDo や PR 説明、必要なコミット本文に明記する。Plan を変更する必要が生じた場合は作業を中断し、更新版 Plan の承認を取り直したうえで ToDo の計画欄も差し替える。
- **緊急対応時の扱い**: ユーザーが緊急を指示した場合でも最小限の Plan を提示し承認を待つ。ユーザーが即時対応を明示したケースでも、後から PR などで Plan と承認の記録を必ず残す。
- **作業中の逸脱禁止**: 承認範囲を超える変更・ドキュメント更新・設定変更は行わない。追加作業が必要になった場合は Plan を再提示して承認を得る。

### Plan 承認と ToDo 転記
- 承認メッセージ ID／リンクを ToDo に記録し、「計画策定」欄へ承認済み Plan を全文転記する。
- Plan を更新する場合は作業を一時停止し、再承認を得たうえで ToDo の内容も差し替える。

### 実作業着手
- 作業ログや判断材料は都度 ToDo に追記し、チェックボックスで進捗を管理する。
- 「更新不要」など結論が同じでも、確認した根拠をメモ欄へ残す。入れ子タスクは子タスク完了後に親タスクも更新する。

#### PR 作成手順
1. PR 作成時は `gh pr create --fill`（または `--template`）を利用し、`.github/pull_request_template.md` を必ず反映させる。
2. テンプレート展開後に追記が必要な項目のみ手動で修正する。`--body` オプションで新規本文を指定しない。
3. ToDo やノートのリンク、コマンドログはテンプレートのチェックリストに沿って記載する。
4. スクリーンショットや PDF などの成果物がある場合は、テンプレートの動作確認欄に添付先を記入する。

#### 完了手順
1. PR 作成（ドラフト解除含む）時に `todo-auto-complete` ワークフローが head ブランチ上で「PR 作成」チェックを完了にしつつ、アーカイブ移動とロードマップ反映を行う（その他の未完タスクは保持される）。ワークフローが失敗またはスキップされた場合は手動で処理し、原因を `docs/notes/` に記録する。
2. 自動処理または手動処理後、ToDo のメモに PR 番号／URL を追記して履歴を明確にする。PR を再オープンした場合は `todo-auto-complete` の再実行結果を確認する。
3. PR マージ後はローカルとリモート両方の作業ブランチを削除し、`git status` がクリーンであることを確認する。

## ガバナンス

### ロードマップ番号の運用ルール
- `RM-xxx` は `docs/roadmap/roadmap.md` に記載されたテーマ番号と一致させる。ToDo を作成する際は、該当 RM がロードマップに存在することを確認する。
- 新規テーマを検討する場合は、以下の手順で循環参照を避ける。
  1. ロードマップ整備タスクとして `RM-000`（ロードマップ保守）で ToDo を起票し、必要な検討とヒアリングを実施する。
  2. 検討結果をもとに `docs/roadmap/roadmap.md` へ新しい `RM-xxx` エントリを追加し、Mermaid 図にもノードを追加する。
  3. 新規 RM を参照する実装タスクを作成する際は、ToDo の `roadmap_item` に `RM-xxx テーマ名` を記載し、ブランチ名にも `rmxxx` を含める。
- `scripts/lint_todo_completion.py` は ToDo の `roadmap_item` が `RM-xxx` 形式で記載されているか、対応する RM がロードマップに存在するかを検証する。PR 作成前に `uv run python scripts/lint_todo_completion.py` で検証し、違反があれば修正する。
