# pptx_generator 開発メモ

- Python 3.12 を使用しているのは、型ヒントの強化と性能向上のため、uv で依存関係を管理することで再現性の高い環境構築を実現している
- テンプレート抽出では python-pptx でレイアウト構造を解析するが、これはクロスプラットフォーム対応と Office アプリケーションを起動しないヘッドレス実行を可能にするため
- Stage 1 でテンプレートから jobspec.json を生成することで、後続 stage がレイアウト情報を再利用でき、テンプレ解析コストを削減できる
- LibreOffice headless モードで PDF 変換を実行するのは、無償で安定した変換品質を確保し、フォント埋め込みと透過画像の再現性を担保するため
- .NET 8 の Open XML SDK で段落スタイルを仕上げるのは、python-pptx では制御困難な低レベルのドキュメント操作が必要だから
- ブランド設定はテンプレートから抽出する TemplateStyle を唯一のソースとし、必要に応じて `pptx template` 出力の `branding.json` を設計メモとして参照する
- Analyzer が余白逸脱やフォントサイズ不足を検出するのは、人的レビューを本質的な内容判断に集中させ、体裁チェックを自動化するため
- 承認ログには slide_id、actor、action、timestamp を記録することで、後から監査時にスライド単位の変更履歴を追跡できトレーサビリティを確保している
- ruff と mypy で静的解析を実施しているのは、コードの品質を維持し、型安全性を担保して実行時エラーを予防するため
- SonarCloud で品質ゲートを監視することで、技術的負債の蓄積を防ぎ、バグ・脆弱性・コードスメルを継続的に可視化している
- samples/templates/ にゴールデンサンプルを配置しているのは、テンプレ更新時の互換性テストとリグレッションチェックに再利用するため
- Conventional Commits でコミットメッセージを統一することで、変更履歴の追跡性を高め、自動リリースノート生成やセマンティックバージョニングに対応可能にしている
- ロードマップは docs/roadmap/roadmap.md で管理しており、ブランチや PR を跨ぐ開発テーマを俯瞰してステータスの起点とするため
- RM-080 はテンプレ実スライドスナップショット強化を目的とし、図形寸法・段落属性を詳細に取得してテンプレ解析と後続 stage での活用を可能にする
- 箇条書きの深さは最大3階層まで制限しているのは、視認性の低下とレイアウト崩れを防ぎ、ブランドガイドラインに沿った体裁を維持するため
- CLI は uv run pptx で起動することで、仮想環境の切り替えを意識せずに統一されたエントリーポイントから実行できる
- テンプレ差分検出で互換性警告を出力するのは、テンプレ更新時のリスクを早期に可視化し、レイアウトやプレースホルダーの変更点を運用チームへ通知するため
- HITL 承認フローは Stage 2 と Stage 3 に配置しており、AI 支援と人間判断のバランスを取りながら品質を掌握する設計になっている
- 監査ログで再現性とトレーサビリティを確保することで、情報システム監査や外部監査に耐える証跡を残し、コンプライアンス要求に対応可能にしている
- prepare_card.json が Stage 2 の出力であり、章構成とスライド素材を正規化した中間データとして後続マッピング処理に引き渡される
- generate_ready.json が Stage 3 の出力であり、レイアウト割付済みの描画直前仕様として Stage 4 のレンダリングで使用される
- proposal.pptx が最終成果物であり、ブランドスタイルを適用した高品質なプレゼン資料として営業・コンサル部門へ配布される
- PDF は任意で生成可能にしており、配布形式の選択肢を広げクライアントへの提出や印刷用途に対応するため
- フォールバック戦略として縮約→分割→付録送りを実装しているのは、テキスト容量超過時に安全に調整し、レイアウト崩れを回避するため
- テンプレ命名規則は厳密にチェックしており、アンカー名の不整合が原因で Renderer が描画できないリスクを予防している
- usage_tags を Template AI で推定することで、レイアウトの推奨用途を自動で整理し、後続 stage のマッピング判断を支援する
- PPTX_TEMPLATE_LLM_PROVIDER=mock でスタティックモードに切り替え可能にしているのは、LLM API を利用しない環境でも基本機能を提供するため
- テストは pytest で実行しており、単体テスト・統合テスト・CLI 統合テストを一括で走らせて品質退行を検知している
- docs/todo/ 配下でタスク管理を行い、ロードマップ番号や関連 Issue と紐付けることで現場計画と戦略方針を接続している
- Approval-First ポリシーで Plan 承認を必須化しているのは、作業開始前にスコープ・リスク・テスト方針を明確化し、意思決定の透明性を確保するため
- ブランチ命名は feat|fix|chore|docs/rmxxx-slug 形式を採用しており、変更種別とロードマップ項目を一目で識別できるようにしている
- main ブランチへの直接 push は禁止しており、必ず PR レビューを経由することでコード品質とドキュメント整合性を担保している
- PR にはテスト結果とロールバック手順を記載することで、リリース後のトラブル時に迅速な復旧を可能にしている
- CI で自動テストと静的解析を実行することで、人的レビュー前にコード品質の最低ラインをクリアし、レビュー効率を高めている
- 北極星指標は月次 120 件の提案書生成を目標とし、開発・運用双方が同じゴールを追って投資優先度を判断できるようにしている
- 手戻り率 10% 以下を目標としているのは、生成された提案書の品質を高め、再提出や修正作業のコストを最小化するため
- 30 スライドを 60 秒以内で出力することを効率指標とし、緊急の提案依頼にも即座に対応できるスピードを担保している
- critical issue は平均 0.5 件以下を目指しており、Analyzer の自動検知精度を高めて人的補正の工数を削減している
- ジョブ失敗時の再実行は 5 分以内を目標とし、可用性とリトライ設計で運用の安定性を確保している
- layouts.jsonl にレイアウト構造を記録することで、テンプレのレイアウト別プレースホルダー情報を後続 stage が参照できるようにしている
- diagnostics.json に診断結果を出力するのは、テンプレ抽出・検証時の問題点を可視化し、テンプレ改善のフィードバックループを回すため
- analysis.json に解析メトリクスを記録することで、生成された PPTX の品質を定量評価し、自動補正の判断材料として活用している
- rendering_log.json にレンダリング履歴を保存しており、描画処理のトレースと失敗時の原因特定を支援している
- audit_log.json で監査証跡を残すことで、入力データ・テンプレバージョン・生成ハッシュ・処理時間を長期保管し外部監査に対応可能にしている
- テンプレ更新時は extract-template CLI で再抽出を実行し、レイアウト構造の変更を確実に反映させて互換性リスクを回避している
- 既存資料の品質診断も実行可能にしており、過去に生成した PPTX のブランド統一状況を可視化してガバナンスを強化できる
- AIレビューでグレード A/B/C 評価を実施することで、承認者が優先的に確認すべき箇所を明示し、レビュー効率を高めている
- Auto-fix 提案の採否をログに記録しているのは、AI の改善提案が人間によってどう判断されたかを追跡し、将来の学習データとして蓄積するため
- コントラスト不足を自動検出することで、アクセシビリティ要件を満たし、視認性の低いスライドを事前に補正している
- グリッドずれを位置スナップで補正するのは、複数担当者が手作業で整える工数を削減し、レイアウトの一貫性を自動で担保するため
- 段落レベル制限で箇条書きジャンプを防止しているのは、階層が飛ぶと視認性が低下しブランドガイドライン違反になるため
- フォント埋め込みで PDF 再現性を確保することで、閲覧環境によるフォント差し替えを防ぎ、配布先での体裁崩れを回避している
- Teams や Slack への通知を想定しているのは、生成完了や失敗時の状況を運用チームへリアルタイムで共有し、一次対応を迅速化するため
- ストレージ保存期間は初期値 90 日としており、監査ログと生成物を一定期間保持しつつストレージコストを管理している
- 機微情報は公開リポジトリに置かないポリシーを徹底しており、セキュリティリスクを予防し、誤ってコミットされた場合も即座に対処できるようにしている
- samples/ に匿名化サンプルを配置することで、実データを使わずにテストや検証を実施でき、情報漏洩リスクを最小化している
- 環境変数で API キーを管理しているのは、認証情報をコードやドキュメントに埋め込まず、安全に外部サービスと連携するため
- UV_CACHE_DIR=.uv-cache で権限問題を回避しており、サンドボックス環境や CI 環境での uv 実行時のエラーを防いでいる
- docs/policies/ に開発ルールを明文化することで、新規参加者がプロセスを理解しやすくし、属人化を排除している
- docs/runbooks/ に運用手順を記録しており、突発対応時のフォールバック策や一次対応手順を共有して運用の安定性を高めている
- docs/notes/ に設計検討議事録を保存することで、意思決定の背景を残し、後から振り返る際の情報源としている
- テンプレ差分レポートで変更点を可視化するのは、テンプレ更新がレイアウトやプレースホルダーに与える影響を事前に把握し、運用リスクを低減するため
- ゴールデンテストでリグレッションチェックを実施しており、コード変更やテンプレ更新時に既存機能が壊れていないことを確認している
- バイナリ比較ではなくハッシュ検証を採用しているのは、PPTX 内部のタイムスタンプや UUID が毎回変わるためバイナリ一致が困難だから
- 複数形式インポートでテキスト・PDF・HTML に対応することで、営業資料や競合分析資料など多様な入力ソースを取り込めるようにしている
- Markdown パースで見出しと本文を抽出するのは、構造化されたテキストから章構成を自動で認識し、スライド分割の判断を支援するため
- 表データは jobspec のテーブルアンカーへマッピングすることで、テンプレートが定義する表プレースホルダーへ確実に配置しレイアウト崩れを防いでいる
- 画像はプレースホルダーのサイズと縦横比を参照してリサイズしており、Analyzer が伸縮率をチェックすることで視覚的な歪みを検出している
- チャート生成は将来拡張として検討中であり、テンプレートのチャートプレースホルダーと JSON のデータ系列を突合する設計案が議論されている
- ビジュアルフィードバックコパイロットは保留扱いで、視覚モデルと LLM がリアルタイムで改善提案を出す構想だが、インフラやコストの面で再開条件を検討中
- ライブ共同編集アシストも保留しており、提案会議中に AI がライブで修正案を提示する即応性の高いプレゼン支援を将来的に実現したい
- レイアウト生成 AI は未着手で、AI が候補レイアウトを提示し承認者が選択するハイブリッドワークフローを検討中だが、まずは既存マッピング機能の安定化を優先している
- 情報ギャップインテリジェンスも未着手で、コンテンツの不足箇所や外部データ参照を AI が示す未来像が描かれているが、優先度は低い
- Story Modeler で業界別ストーリー基盤を整備したことで、提案書のストーリーラインを AI が共同設計できるようになり、Stage 3 でのストーリー要素取り込みを支えている
- コンテンツ承認オーサリング基盤を完了したことで、Stage 2 での承認メタデータ整備が進み、HITL フローの土台が固まった
- Analyzer Review Engine 連携も完了しており、Stage 3 のドラフト評価で Analyzer の指摘を活用して品質判断を支援できるようになった
- ドラフト構成承認フローを整備済みで、章レーンやページ遷移を人が調整し、レイアウトヒントと付録送りの判断を残した draft_approved.json を作成できる
- テンプレート命名整合性チェッカーを実装したことで、アンカー名のズレや命名ルール違反を自動検出し、テンプレ品質の土台を固めた
- テンプレ資産監査パイプラインを構築することで、テンプレ版ごとの差分を継続検証しながらブランド別のゴールデンテンプレをバージョン管理する基礎体力を築いた
- レイアウト解析検証を強化したことで、テンプレ構造の自動点検精度が向上し、レイアウトやプレースホルダーの不整合を早期検知できるようになった
- Analyzer 構造抽出差分連携を整備したことで、テンプレ更新時のリスクを早期検知し、互換性警告や代替案を通知できるようになった
- README に多言語展開予定があるが未着手で、英語版ドキュメントの整備により海外開発者の参加を促進したいが、まずは日本語版の充実を優先している
- OSSとして MIT ライセンスで公開しているのは、組織の文脈に合わせた拡張を容易にし、コミュニティからのフィードバックを得てプロダクト改善を加速するため
- GitHub でイシュートラッキングを行い、バグ報告や機能要望を一元管理して開発優先度の判断材料としている
- CONTRIBUTING.md で開発プロセスを明示することで、新規コントリビューターがルールを理解しやすくし、PR レビューの効率を高めている
- コミュニティからのフィードバックを歓迎しており、外部の視点から品質改善や新機能のアイデアを取り込んでプロダクトを進化させたい
- 営業・コンサル部門の負荷軽減が目的で、提案書・分析レポート・施策計画など多様な資料を短期間で量産する現場の工数を削減したい
- 提案書作成工数 70〜80% 削減を目指しており、人的作業が多い整形・割付・体裁チェックを自動化することで現実的な目標として設定している
- ブランドガイドライン準拠率 100% を設計値とし、逸脱時は監査ログで原因箇所を即トレースできるようにして品質の均一化を徹底している
- 属人化を排除し組織のナレッジを資産化することで、担当者の異動や退職時にも業務が滞らず、再現性の高い運用を実現したい
- 夜間バッチで翌朝レビュー可能な運用を想定しており、案件情報を投入すれば翌朝に提案書を受領できる無人生成フローを実現している
- 会議直後の示唆を即ドラフト化することで、動的生成モードで柔軟に内容を組み替え、AI レビューと人間の承認を繰り返しながら最適化できる
- 動的生成モードと静的生成モードを切り替え可能にしており、初期ドラフトは動的、最終量産は静的という運用で現場のスピードと品質基準を両立している
- Mac / Linux / Windows で同一フローを提供することで、開発環境や運用環境の差異を吸収し、クロスプラットフォーム対応を実現している
- ヘッドレス実行で CI/CD 環境にも統合可能にしており、自動テストや自動デプロイのパイプラインに組み込んで品質保証を自動化している
- REST API 化も将来構想に含まれており、CLI と共通のコアロジックを再利用してジョブキューとストレージ通知を組み合わせた SaaS 展開を議論している
- キュー駆動バッチ運用も検討中で、夜間ジョブをワーカーへ配分し、失敗したスライドだけ再処理する差分リラン戦略を計画している
- マイクロサービス化で水平スケール対応予定であり、テンプレ解析やレンダリング処理を分離して月次 120 件の提案書生成要件を達成したい
